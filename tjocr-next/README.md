# TJOCR Next

Новая самостоятельная версия сервиса распознавания рукописного таджикского текста (HTR/OCR).
Разработана в соответствии со спецификацией `docs/rebuild/` на базе Next.js 15, TypeScript, Supabase и Vercel Serverless.

---

## Архитектурные принципы

1. **Единый современный стек**: Next.js App Router, React 19, TypeScript strict mode, серверные функции Vercel Node.js.
2. **Изоляция и приватность данных**: Supabase Auth (настоящий анонимный режим гостя + привязка постоянного аккаунта), PostgreSQL с полным покрытием RLS, приватный Supabase Storage бакет.
3. **Обход платформенных лимитов**: Прямая загрузка файлов > 4.5 МБ из браузера в Storage через Signed Upload URL, исключая таймауты и ошибку 413 Payload Too Large серверных функций Vercel.
4. **Устойчивые фоновые задачи (Durable Jobs)**: Хранение состояний и шагов в БД (`jobs`, `job_outbox`). Перезагрузка страницы или закрытие вкладки не приводят к потере прогресса.
5. **Нейтральность OCR-движка**: Полная абстракция `LineDetector` и `TextRecognizer`. Никаких жестко зашитых названий сторонних моделей в кодовой базе и пользовательском интерфейсе. Подключение будущей TrOCR с LoRA/rsLoRA через специализированный сервис инференса.
6. **Дизайн Geist / Vercel**: Монохромная палитра, четкая типографика, фокус на рабочем документе, отсутствие декоративного шума и фиктивных метрик.

## Настройка окружения

1. Скопируйте шаблон переменных окружения:
   ```bash
   cp .env.example .env.local
   ```
2. Заполните ключи в `.env.local`:
   - `NEXT_PUBLIC_SUPABASE_URL` — адрес вашего проекта Supabase.
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY` — публичный anon-ключ.
   - `SUPABASE_SERVICE_ROLE_KEY` — приватный ключ сервисной роли (только для сервера).
   - `SUPABASE_STORAGE_BUCKET` — имя бакета (например, `htr-uploads`).
   - `OCR_API_BASE_URL`, `OCR_API_KEY`, `OCR_MODEL_ID` — конфигурация провайдера OCR.

## Применение миграции в Supabase

1. Откройте **SQL Editor** в вашей панели Supabase.
2. Скопируйте и выполните содержимое файла:
   `supabase/migrations/20260914000001_initial_schema.sql`
3. Миграция создаст:
   - Все необходимые таблицы с внешними ключами и каскадным удалением.
   - Строгие RLS-политики (доступ только для `auth.uid() = owner_id`).
   - Приватный Storage бакет `htr-uploads` и политики доступа к файлам.

Для Этапа 2 примените следующую миграцию после initial schema:
`supabase/migrations/20260915000002_stage2_auth_quota_ttl_security.sql`.
Она добавляет атомарное создание документов с квотой, гостевой TTL 7 дней,
квоту аккаунта 100 документов/1 ГБ за 30 дней, безопасные RPC и Storage update
policy. Гостевые документы не переносятся в новый аккаунт отдельной записью:
регистрация через текущую гостевую cookie-сессию обновляет пользователя, поэтому
его документы сохраняют владельца.

В Supabase Auth включите **Manual linking** и для режима без кода отключите **Confirm email**. Если оставить
подтверждение включённым, API вернёт `EMAIL_CONFIRMATION_REQUIRED`, не выдавая
ложный успешный вход. `SUPABASE_SERVICE_ROLE_KEY` нужен только для очистки cron и
межрегионального rate limit; он никогда не должен попадать в `NEXT_PUBLIC_*`.

Vercel Cron вызывает `/api/v1/maintenance/cleanup` каждый час. Передайте ему
секрет `CRON_SECRET` и не открывайте этот маршрут без заголовка
`Authorization: Bearer <CRON_SECRET>`.

## Запуск приложения

Установите зависимости и запустите локальный сервер:
```bash
npm install
npm run dev
```

Приложение будет доступно по адресу `http://localhost:3000`.

Для локальной разработки запускайте один `npm run dev`. Development-кэш Next.js
изолирован в `.next-dev`, поэтому параллельный `npm run build` не удаляет chunks
у работающего dev-сервера. После смены переменных окружения перезапустите dev.

Проверки второго этапа:
```bash
npm run typecheck
npm test
```

Для тестирования Этапа 0 откройте страницу:
`http://localhost:3000/test-phase-0`
